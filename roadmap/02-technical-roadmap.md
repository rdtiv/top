# Try Omarchy daily-driver: problems to solve, in order

As of 2026-09-22. Anchored to upstream main at commit `7f3ce66` (unreleased; last tagged release v0.4.1, 2026-09-15). Measurements are from the installed 0.4.0 app on macOS 26.6.2 (25G83). Status: first draft, for discussion; a starting point for a more refined roadmap, not the roadmap. First written 2026-09-16 against `58cbac5`; this revision absorbs the 29 pull requests merged since.

## TL;DR

This is the engineering companion to the executive briefing: a graph of the problems standing between Try Omarchy — the macOS app that runs the Omarchy Linux desktop inside a virtual machine on an Apple silicon Mac — and the claim that it is a daily driver. It is ordered by what blocks what: Horizon 0 must land before anything below it is worth doing, Horizon 1 is what a v1 release gates on, and Horizon 2 is deliberately after v1. The four Horizon 0 problems, in plain words: the app has not been proven on macOS 27.0, which Apple released on 2026-09-14 and which is where three of the four open launch reports come from; the rest of pipe 2 — the kernel pair, the graphics runtime, the package holds and the reviewed backports — still reaches an existing virtual machine only through a destructive factory reset, now that an integration manager exists and host-bridge scripts and services are the obvious first payload to widen it with; the small guest programs that bridge the virtual machine to the Mac accumulate failures over days of uptime; and Try's part of packaging convergence, which has become a policy choice rather than a missing channel. Velocity is itself a finding: 29 pull requests from 13 people landed on main between v0.4.1 and 2026-09-22, most of them on 2026-09-21 and 22, which makes "what to say no to and what to write down" at least as valuable here as "what to build". One Horizon 0 candidate is held open pending evidence: #230, Chromium-family browsers crash-looping their GPU process on virgl and taking the guest with them, which belongs in Horizon 0 if it reproduces on a released macOS, because the browser is the daily-driver workload. Use it two ways: file issues straight from the rows in sections 2 to 6, each of which already carries an owner, a dependency, its evidence and its risk; and lift section 8 into the repository as a release-readiness document, rewriting as you go. Section 0 defines the terms and the conventions, and nothing here is assigned to anyone.

### Terms used

Defined once, here: the projects and people this document names, plus the terms the body does not gloss at first use. Everything else — virglrenderer, ANGLE, 16 KiB pages, foot-candles, Tailscale, pacman and the ALPM guard, initramfs, `vulkan-swrast`, RDP and the rest — is glossed inline where it first appears.

- **Omarchy**: the opinionated Linux desktop built on Arch Linux and the Hyprland window manager that runs inside the virtual machine.
- **Try**, or **Try Omarchy**: this project — the macOS app that runs Omarchy in a virtual machine on Apple silicon.
- **Guest** and **host**: the Linux system inside the virtual machine, and the Mac running it.
- **VMM** (virtual machine monitor): the program that creates and runs a virtual machine. Here that is **QEMU**, the open-source VMM Try uses, driving Apple's low-level **Hypervisor.framework** (**HVF**), which lets a user-space program run guest CPU instructions on the real processor. Apple's higher-level **Virtualization.framework** (**VZ**) is a different API with its own built-in device models, and not the one Try takes.
- **EL2** and **nested virtualization**: EL2 is the ARM processor privilege level a hypervisor runs at, and exposing it to the guest is what lets the guest itself run virtual machines.
- **virtio**: the standard family of paravirtualized devices a guest uses instead of emulated hardware — graphics, serial channels, the memory-reclaim balloon, folder sharing, keyboard, tablet and a custom pinch device.
- **QMP** (QEMU Machine Protocol): QEMU's JSON control channel, which Try uses to pause, resume and power down the guest.
- **Cocoa**: macOS's native application framework; QEMU's Cocoa display backend is the Mac window the guest is drawn into.
- **aquamarine** and **hyprtoolkit**: two libraries Hyprland depends on and whose versions must match it, which is why Try rebuilds all three together.
- **Arch Linux ARM**: the community aarch64 port of Arch Linux that supplies the guest's ordinary packages.
- **PKGBUILD**: the Arch recipe file that describes how to build a package.
- **omarchy-pkgs**: the Omacom repository that builds and signs Omarchy's own packages. **edge/aarch64** is its rolling pre-release channel for 64-bit ARM.
- **boot kit**: the kernel, initramfs and kernel command line saved next to a particular virtual machine disk, so an app update never boots an old disk with a new kernel.
- **factory image** and **factory reset**: the Linux disk image Try builds and ships inside the app; a factory reset discards the user's virtual machine and starts again from a fresh copy of that image.
- **pipe 1** and **pipe 2**: the two update channels. Pipe 1 is Omarchy's own updater advancing ordinary packages, which works today. Pipe 2 is delivery of Try's own kernel, runtime and backports to an existing virtual machine; on main it exists for host integrations through the integration manager and for nothing else.
- **integration manager**: the pipe-2 mechanism shipped on main in PR #193. The app exposes a dedicated read-only 9p share to the guest; a guest command reviews and installs hash-verified bundles of Try's own guest-side features, with root-private backups and resumable receipts, without a factory reset. Its first payload is sudo Touch ID.
- **free-page reporting**: the guest telling the host which memory pages it has stopped using, so the host can reclaim them.
- **UEFI**: the standard firmware stage a machine normally boots through. Try skips it and boots the kernel directly.
- **vCPU**: a virtual CPU presented to the guest.
- **DMG** and **notarization**: the Mac disk-image format releases ship in, and Apple's scan that lets a signed app open without warnings.
- **Omarchy M**: the team announced on 2026-09-11 to bring Omarchy to Apple silicon Macs, both natively and in a virtual machine.
- **Omarchy Dragon**: the equivalent team for Snapdragon X laptops, announced 2026-09-18, with its own aarch64 package owner. It shares the ARM package channel with Omarchy M, which is why packaging ownership in this document names a channel rather than a person.
- **try-omarchy-windows**: the Windows counterpart GitHub project under the same organisation — the same idea on a different hypervisor — used here as a process template. It declared v1.0.0 in its README and changelog on 2026-09-22; no release tag yet.
- **omarchy-mac**: the native dual-boot project, where Omarchy is installed beside macOS rather than run in a virtual machine.
- **Asahi**, or Asahi Linux: the community project that reverse-engineered Apple silicon so Linux can run natively on it; it supports M1 through M3, and M4 is not installable today.
- **Parallels**: the commercial Mac virtualization product the Windows VM runs in, beside Try on the same Mac. Windows always runs beside Try, never inside the Omarchy guest.
- **themartiano**: the GitHub handle of Eduardo, Try Omarchy's maintainer.
- **Fail-Safe**: the GitHub handle of Try Omarchy's most active outside contributor and reviewer.
- **Shun Li**: the contributor building aarch64 package support in omarchy-pkgs.
- **rdtiv**, **nocell**, **caius72**, **vzxxbacq**, **drdator**, **MatthewFeroz**, **Mahognes**, **jean-humann**, **dyl-joseph**, **k5953837**, **xavierforge**: GitHub handles of contributors and reporters whose issues and pull requests are cited by number below. **ryanrhughes** is the omarchy-pkgs maintainer who closed the large aarch64 build pull request in favour of smaller ones.
- **#NNN**: an issue or pull request number in `omacom/try-omarchy` unless another repository is named.

### The security model as shipped

Stated once, here, so that later rows can say "this changes the security model" and mean something specific. QEMU runs as the user under Hypervisor.framework entitlements, so the VMM — not an Apple XPC helper, a background process supplied by macOS — owns guest RAM (`macos/build-qemu-gpu-runtime.sh:61-65, 501-522`, HVF-only, with QEMU's software CPU emulator TCG compiled out). Camera and microphone reach the guest only through host bridges the Mac user granted to the app: capture through AVFoundation, Apple's media framework, at 1280x720 NV12 into a guest `v4l2loopback` virtual-webcam node, on demand (`docs/architecture.md:75-82`); audio through `intel-hda`, an emulated sound card, and a route directory. Touch ID is sudo-only: a non-exportable P-256 key in the Secure Enclave — the isolated security processor on Apple silicon — bound to a root-private random guest ID, a signed challenge with a 15-second validity window, registration in Linux's PAM authentication stack as `sufficient` with password fallback, and explicitly "does not authenticate login or screen-unlock flows" (`docs/architecture.md:84-112`). Fail-Safe's summary on try-omarchy #133 is the right public phrasing: it "is cryptographically paired with the Mac's Secure Enclave. Applications receive an authentication result, not fingerprint data". Port forwards are loopback-only, TCP and UDP, at most 32 rules, NAT only — network address translation, where the guest shares the Mac's address rather than taking its own (`macos/qemu-port-forwarding.sh`). The 9p share — one Mac folder exported into the guest over the 9p network filesystem protocol — runs `security_model=none`, so every host file operation runs as the Mac user, with a QEMU patch remapping ownership to guest uid/gid 1000 (`docs/architecture.md:114-122`). Bridged networking is a shipped opt-in in v0.4.0 via a privileged `socket_vmnet` daemon registered through macOS's SMAppService background-service API, one bridged session per Mac (`README.md:236-237`), and it is the one shipped feature that widens the model beyond loopback.

Anything below that changes this paragraph says so in its own row.

## 1. The two update pipes

Try Omarchy has two update paths that look like one from the outside. Collapsing them is the single most expensive documentation error available here, because a reader who collapses them concludes "people can already run `omarchy update`, so updates are solved."

```
                        PIPE 1  (shipped, works)
  ┌──────────────────────────────────────────────────────────────────┐
  │  omarchy update  inside the guest                                │
  │    lock → free-space check → paccache → snapper → pacman -Syu    │
  │    (snapper is a no-op in this guest: no btrfs, no snapper)      │
  │    under OMARCHY_UPDATE_PACMAN=1 → omarchy-migrate → restart     │
  │                          │                                       │
  │                          ▼                                       │
  │    ALPM guard hook 00-omarchy-update-guard.hook blocks raw       │
  │    pacman -Syu unless OMARCHY_ALLOW_DIRECT_PACMAN=1              │
  │                          │                                       │
  │                          ▼                                       │
  │    pre-refresh-pacman hook restores the aarch64 pacman files     │
  │    from /usr/share/try-omarchy/ after a channel refresh writes   │
  │    x86_64 templates to /etc                                      │
  │                          │                                       │
  │                          ▼                                       │
  │    ordinary Arch Linux ARM packages advance                      │
  │    OWNER: Omarchy upstream (pipeline) + Try (the ARM restore)    │
  └──────────────────────────────────────────────────────────────────┘

                        PIPE 2  (exists for host integrations)
  ┌──────────────────────────────────────────────────────────────────┐
  │  INTEGRATION MANAGER (#193) — the designed route, shipped        │
  │    a read-only 9p share at /mnt/try-omarchy-updates              │
  │    a hash-verified bundle, reviewed in the guest before install  │
  │    root-private backups, resumable receipts                      │
  │    a status port reporting to the Mac every ten seconds          │
  │    first payload: sudo Touch ID, and nothing else yet            │
  │                          │                                       │
  │                          ▼                                       │
  │  three ad hoc routes carry what the manager does not:            │
  │    #152  guest entry points via a separate read-only boot share  │
  │    #185  a manual repair-update-holds.py (root, --apply)         │
  │    #243  memory reclaim, on the next launch of an updated app    │
  │                          │                                       │
  │                          ▼                                       │
  │  STILL RESET-ONLY:                                               │
  │    direct-boot kernel + matching headers                         │
  │    packaged try-omarchy-runtime and the graphics stack           │
  │    package holds (manual repair only)                            │
  │    reviewed compatibility backports (16 on main, hash-paired)    │
  │                          │                                       │
  │                          ▼                                       │
  │   for those, the ONLY delivery vehicle is:  Factory Reset        │
  │   (destructive: new writable disk, new boot kit, /home gone)     │
  │                          │                                       │
  │                          ▼                                       │
  │    OWNER: Try, alone. No upstream component can supply this.     │
  └──────────────────────────────────────────────────────────────────┘

        App release  ──►  new bundled factory  ──►  applies to NEW or
        (DMG, signed,     disks only. An existing VM keeps its own
         notarized)       paired boot kit and is never rebased.
```

The architecture document states both halves without hedging. Pipe 1: "Omarchy's built-in updater may advance ordinary packages supported by this ARM guest, but the direct-boot kernel and matching headers, the packaged `try-omarchy-runtime`, and reviewed compatibility backports remain pinned in Try Omarchy's prioritized local repository." Pipe 2, in the wording main now carries: "The bundled integration manager provides an explicit migration channel for reviewed guest integrations, with user-approved installation and per-VM status reporting. It does not replace the pinned kernel or reproduce every factory change. Factory reset remains the way to opt into the complete new factory" (`docs/architecture.md`, main; at `58cbac5` the same passage read "Delivering new Try Omarchy runtime or backport revisions to existing disks requires an explicitly designed in-guest migration channel; today a factory reset is the way to opt into the complete new factory", `docs/architecture.md:263-272`). The user-facing README says the same thing in user words: "A confirmed reset is the deliberate, destructive way to start again from the newest bundled factory" (`README.md:408-415`, unchanged on main).

**What pipe 2 is on main, exactly.** PR #193 (Fail-Safe, merged 2026-09-21) built the mechanism the diagram lists and shipped it with one payload. Beyond the diagram: the guest mounts the share at `/mnt/try-omarchy-updates`, reviews the bundle's inventory and hashes before anything is written, asks for the Linux user's sudo authorization, keeps backups private to root under `/var/lib/try-omarchy/integrations`, and records progress per component so an interrupted install resumes rather than restarts, while "A dedicated virtio port carries bounded status reports to the host every ten seconds". The boundary is stated in the same document, and it is the sentence this section turns on: the manager "does not replace the kernel, upgrade the graphics stack, repair package holds, install 1Password integration, or reproduce every change in a newer factory image" (`docs/integration-updates.md`, main). The three ad hoc routes carry their own wording: #152 installs its guest entry points "through an idempotent installer on a separate read-only boot share"; #185's standalone `repair-update-holds.py` previews by default and needs root plus `--apply`; and #243's memory reclaim "needs an updated runtime and a VM restart, not a new guest disk" (`docs/memory-reclamation.md`, main).

**Why the paired boot kit makes this harder than it looks.** Each persistent VM keeps its own boot kit — `boot/<identity>/{kernel,initramfs,command-line,metadata.json}` — next to its disk, and "Normal launch selects those saved boot files instead of combining an older root filesystem with a newer bundled kernel" (`docs/architecture.md:192-225`). That design is why a new app release can launch an existing VM without decompressing or cloning a new factory disk, but it means the kernel and the root filesystem advance as a *pair*, per disk, on the host side. A payload that wants to update the guest's local repository cannot ride in the initramfs — the small in-memory filesystem a kernel starts with — of a kit that is already frozen against that disk.

**The in-family precedent.** try-omarchy-windows already solved the repository half of this with a "compatibility revision" mechanism, described in its `docs/GUEST-UPGRADES.md`: "The authenticated image carries the local package repository in its initramfs. At boot, a service checks the payload hashes, copies new package archives, and replaces the repository database atomically. It does not run pacman or modify its lock. Old archives remain available to transactions that read the previous repository. An older image cannot lower the repository's runtime version." The user-facing half is one sentence: "Resetting the installation is not required." That precedent is now a completed process as well as a mechanism: try-omarchy-windows declared v1.0.0 in its README and changelog on 2026-09-22, and retired its public readiness document, `docs/V1-READINESS.md`, on 2026-09-20 in a commit titled "Remove the public v1 roadmap", leaving the compatibility-revision mechanism in place.

**The Mac twist.** On the Windows side the authenticated image travels with the app and the guest boots from it; carrying the payload in the initramfs is free. On the Mac the boot kit is paired per disk and deliberately *not* refreshed by an app update, so the payload has to travel separately from the initramfs.

**Candidate path, presented as a candidate and not a decision.** The shape no longer has to be invented, because #193 shipped it. The proposal is to consolidate and then widen. Consolidate first: #152's boot share, #185's manual command and #243's runtime-plus-restart each solved one delivery problem in its own way, and four routes into one disk is a maintenance surface rather than a channel. Then widen the manager's payloads in a deliberate order. Host-bridge scripts and their systemd services first, because they are the class that rots (section 2.3), because they are files rather than packages, and because the manager already knows how to replace managed files after showing the user what differs. Package holds next, which retires #185's manual repair command. Then the reviewed compatibility backports Try carries ahead of upstream, which is where the local repository and the atomic database swap borrowed from try-omarchy-windows come in. And the kernel and matching headers last, through an explicit, validated boot-kit upgrade — a second, rarer, user-confirmed transition that reuses the existing two-pass consent handshake, in which the user confirms twice, already written for schema-2 recovery, the one-time recovery boot for VMs created before paired boot kits existed (`docs/architecture.md:192-225`). The invariants the manager already holds are what make widening safe: it never runs pacman — Arch Linux's package manager — never touches the transaction lock, and refuses to install while a package transaction is open, so it composes with pipe 1 and with the ALPM guard, the hook Omarchy installs to block direct pacman use, rather than going around either. Split that way, the common case (the runtime package, the backports, the overlay binaries) becomes routine and the rare case (a change to the kernel's ABI, the binary contract everything built against it depends on) stays explicit.

That split — and whether the widening happens in that order — is the design question, and it is **your call**. The rest of section 2 assumes only that pipe 2 keeps widening.

## 2. Horizon 0 (P0): stay alive and stay current

### 2.1 macOS 27 readiness (and the one macOS 26 report)

- **Today.** Four open launch reports, three of them on macOS 27.0 — build 26A428, released 2026-09-14, the operating system a new Mac now ships with and Software Update offers everyone else. try-omarchy #231 (2026-09-18) is the one with a diagnosis. A MacBook Air M2 on 27.0 launches the app, no window appears, and the process quits; a second reporter confirms the same on a Mac mini M4 running v0.4.1. The reporter separates two failures. The QEMU abort inside `hvf_set_phys_mem` during the nested-virtualization probe is real but is not the bug: "The script handles this correctly (falls back to EL1 path). This alone is not the problem." The bug is above QEMU — the system log shows macOS 27 sending a Quit AppleEvent to `omarchy-vm-helper` seconds after launch ("Handling Quit AppleEvent", then "Attempting sudden termination"), which takes the successfully booted guest down with it, while running the launcher script directly bypasses the Swift app entirely: "VM boots successfully to `omarchy-factory login:` prompt with full VirGL rendering." The fixes the issue suggests are all host-app lifecycle knobs — `NSSupportsAutomaticTermination` set to NO in Info.plist, a registered background activity, or `NSProcessInfo.beginActivity`. try-omarchy #250 (2026-09-22) is the same class seen from the user's side: the official v0.4.1 DMG with a verified signature, macOS 27.0 (26A428), an existing persistent disk, three attempts, each ending at "The app's virtual machine stopped during startup", with no new app crash report and a guest console that received no new output. try-omarchy #213 (2026-09-15) is a fresh 0.4.0 download on an M4 Pro whose host is reported as "Golden Gate 27.0". The fourth report is the one that is not macOS 27. try-omarchy #151 (2026-09-07): Try Omarchy 0.4.0, QEMU 11.1.1, Apple M4, macOS 26.3 (25D125), existing persistent disk, 8 vCPU / 4 GiB; QEMU killed outright by macOS (SIGKILLed) about 3.47 s after launch with `EXC_GUARD` / `GUARD_TYPE_VIRT_MEMORY` / `DEALLOC_GAP`, stack `hv_vm_unmap` → `hvf_set_phys_mem` → `address_space_update_topology_pass` → … → `pflash_mem_write_with_attrs` → `hvf_arch_vcpu_exec`; the reporter states "No workaround is claimed." A source-triage comment added on 2026-09-16 reaches the same function from the other end: in the QEMU revision the builder pins, `hvf_set_phys_mem()` "sets `add = false` when the GPA or size is not host-page-aligned, then calls `hv_vm_unmap(gpa, size)`", and an upstream QEMU patch proposal "changes that branch to return immediately and describes the existing path as unmapping a region that was never mapped" — with the commenter's own caveat that "this is a patch proposal, not a verified fix for this report."
- **Why it matters for daily-driver.** Two things at once. The operating system: an app whose first-run experience on a released macOS is a window that never appears, or an alert telling the user to reinstall, has no daily-driver claim to make on the current Mac, and this gate is due now rather than prospective. The hardware class underneath it: M4 has no native alternative. Asahi shipped M3 support in September 2026 (M3 Ultra, GPU, and full DCP — the display coprocessor — excepted) and the M4 feature page lists the installer as "no" with features TBA and DART/PCIe (Apple's memory-address translation unit and the peripheral bus, which most other devices depend on) TBA ([Asahi M4 feature support](https://asahilinux.org/docs/platform/feature-support/m4/)). For an M4 owner Try is not a compromise, it is the only path — and #231's second reporter, #213 and #151 are all on M4.
- **Candidate path.** Reproduce on 27.0 first: launch the shipped app on a 27.0 machine and watch whether the helper is asked to quit. Then read #231's follow-up comment, which settles the mechanism: the system log shows `_kLSApplicationWouldBeTerminatedByTALKey=1` and then "Handling Quit AppleEvent", macOS's automatic-termination machinery deciding that an `LSUIElement` helper with no visible window of its own is eligible to quit. macOS 27's rules exempt only apps with "a visible presence on screen, such as an icon in the upper right part of the menu bar, or a visible window" (support.apple.com/125671), and Squirrel.Mac's updater helper was killed the same way the same week (Squirrel.Mac #336: 30 of 30 installs on 26.7, 12 of 30 on 27.0). That makes the lifecycle change one work item in the launcher (`NSSupportsAutomaticTermination` NO, an activity assertion for the VM's lifetime, and a menu-bar status item, which is also what the integration status needs) and the probe abort a separate, non-fatal follow-up. Treat them as two work items. The Quit AppleEvent is a host-app lifecycle question in the Swift launcher — whether an `LSUIElement` background agent supervising a long-running child process should declare itself ineligible for automatic termination, and which of the three mechanisms the reporter names is right — and it is separate from the probe abort underneath it, which the launcher survives by falling back to the EL1 path. While the probe is in view: macOS 15 is already excluded from it because "its paused probe can succeed even though QEMU later aborts with `HV_BAD_ARGUMENT`" (`docs/architecture.md:39-48`, `macos/run-qemu-gpu.sh:1471-1500`, issue #211), a precedent for treating a probe result as advisory rather than fatal. #250 then tests whether fixing the lifecycle is sufficient, since its symptom is the app's own startup alert rather than a silent disappearance. #151 stays its own QEMU-side investigation: whether the unaligned-unmap branch is actually exercised, which the triage comment says needs the faulting unmap's address and size from QEMU's existing `hvf_vm_map` and `hvf_vm_unmap` trace events on an affected host, before anyone considers a backport. Worth establishing alongside: whether an existing persistent disk is required to reproduce, since #151 and #250 both had one and #213 does not record it. A macOS-version and chip matrix in the issue template would make the next ten reports self-triaging.
- **Owner.** Try for the helper's lifecycle and for the memory topology it hands HVF; QEMU or Apple if what remains is below Try's line. Try cannot fix `hv_vm_unmap` semantics, but Try chooses when and how it unmaps, and Try owns whether its own app survives being asked to quit.
- **Dependency.** None. This is the root of the graph.
- **Horizon.** 0.
- **Evidence anchors.** try-omarchy #231 and its 2026-09-18 root-cause comment; try-omarchy #250; try-omarchy #213; try-omarchy #151 and its 2026-09-16 source-triage comment; `macos/build-qemu-gpu-runtime.sh:61-65, 501-522` (the pinned QEMU revision that triage reads); `docs/architecture.md:39-48`; `macos/run-qemu-gpu.sh:1471-1500`; v0.4.1 release notes (which fix #215 and #216 only); M4 Pro measurement notes for the negative result on the 24 GB test bed: two launches of the installed 0.4.0 app on macOS 26.6.2 booted and ran until powered down, no qemu crash reports exist in `~/Library/Logs/DiagnosticReports`, and a v0.3.0-era guest held one continuous 8 d 21 h boot on that machine.
- **Risk.** The negative result is ambiguous in a newly specific way: one M4 Pro at 26.6.2 not crashing says nothing about macOS 27, because the test bed has never run it. The second risk is fixing one half of #231 and closing it — the probe abort and the Quit AppleEvent are independent, so a helper that survives termination on a machine whose probe still aborts is next week's report. The third is folding #151 into the macOS 27 class because it shares a function name; it is a different operating system and a different signature, and the triage comment gives it its own lead.
- **If "daily driver" ships without it.** The claim is made on an operating system where the app may not start at all, to a hardware class that has no native alternative, and the first-run experience is an app that vanishes or an alert that says to reinstall. Every other row in this document becomes conditional.

### 2.2 Pipe 2: what the integration manager does not carry

- **Today.** Pipe 2 exists for one kind of payload and not for the others. Section 1 has the mechanism and the boundary sentence; what belongs here is the remainder. The integration manager (#193, Fail-Safe, merged 2026-09-21) carries reviewed guest-side integrations, and its design note says the same from the implementer's side — "Kernel and graphics package replacement are excluded" (`integrations/DESIGN.md`, main). What therefore still requires a destructive factory reset is the expensive half of the pinned set: the direct-boot kernel and matching headers, the packaged `try-omarchy-runtime` and the graphics stack pinned against it, and the sixteen reviewed backports with hash pairs on main (thirteen at v0.4.1, `guest/spec.json:239-466`). Package holds are reachable, but only by hand: #185 ships `guest/scripts/repair-update-holds.py` as an explicit maintenance command and is blunt about the limit — "Existing guests must explicitly run the repair; merely updating the Mac app still does not migrate them." And the host-integration binaries in `/usr/local/bin` staged from `guest/native-overlay` are still, per the field write-up (unpublished notes from running this guest day to day on the M4 Pro test bed), "not owned by any pacman package" at all, so no package manager in either pipe can advance them — which is exactly why they are the natural first widening. Upstream Omarchy now carries its first architecture guard: the 2026-09-14 kernel migration (`omarchy migrations/1789325478.sh`) exits on non-x86_64 hosts because `linux-omarchy` is x86_64-only, so pipe 1 will not try to install that kernel here; nothing enforces the same guard on future migrations that touch the kernel, Limine, or Snapper.
- **Why it matters for daily-driver.** A daily driver accumulates state: dotfiles, SSH keys, shells of work, `~/.claude`, a year of git worktrees. If the only way to take a new backport, a newer kernel, or the graphics stack it is pinned against is to destroy that, nobody takes it, and the installed base diverges permanently from the shipped factory. The v0.3.0-era guest in the field write-up shows the shape: it ran 8 d 21 h continuously while predating the fcitx5 drop-in — a small override file for the systemd service manager, covering the guest's input-method service — that had already merged as try-omarchy #91 → #106 on 2026-09-04, and it never received it. What changed this month is that such a guest can now be told about a fix at all; what has not changed is that the fix cannot be a kernel, a runtime, or a backport.
- **Candidate path.** Section 1's consolidate-then-widen order applies here unchanged. What is specific to this row is the first payload: 2.3's audio-bridge leak is the test case, because the fix and the delivery problem are the same problem. Compose with pipe 1 through the ALPM guard rather than around it (`omarchy docs/update-process.md:63-98`); #185 exists precisely because the `pre-refresh-pacman` hook "restores `/usr/share/try-omarchy/pacman.conf`" over a hand-edited `/etc/pacman.conf`, the same lesson learned the expensive way (`docs/architecture.md:187-190`). One development to track: omarchy-pkgs PR #591 proposes `linux-aurora`, an Apple-silicon kernel for the edge and rc channels. If it lands, the kernel pair has a candidate source outside Try, and the last step becomes pairing the disk with a channel-installed kernel rather than shipping one from the app bundle.
- **Owner.** Try, alone. Nothing in Omarchy upstream, omarchy-pkgs, or QEMU can supply this; it is a Try-specific runtime and Try-specific backports being delivered to a Try-specific disk layout.
- **Dependency.** 2.1 (a channel to a machine that cannot launch is not useful). Interacts with 2.4: the more Try's local repository shrinks toward the signed aarch64 channel, the less pipe 2 has to carry.
- **Horizon.** 0. This is the row that turns "persistent VM" into "maintained VM", and it is now half-done rather than absent.
- **Evidence anchors.** `docs/integration-updates.md` (main); `integrations/DESIGN.md` (main); try-omarchy PR #193; try-omarchy PR #185; try-omarchy PR #152; try-omarchy PR #243 with `docs/memory-reclamation.md` (main); `docs/architecture.md` (main) for the update-channel paragraph and `docs/architecture.md:263-272` for what that paragraph said at `58cbac5`; `README.md:408-415`; `docs/architecture.md:192-225`; `guest/spec.json:239-466`; `omarchy docs/update-process.md:63-98`; `docs/architecture.md:186-193`; try-omarchy-windows `docs/GUEST-UPGRADES.md`; the author's unpublished field write-up on the fcitx5 restart loop.
- **Risk.** Scope creep into a general-purpose updater. The mechanism that works is deliberately narrow — copy archives, swap a database atomically, never mediate a transaction — and #193 held that line. Second, trust: the payload is code entering an existing VM, which is why the manager's documentation is careful that hashes "detect corruption and do not independently establish trust in an app". Third, and the reason this row says consolidate before widen: four delivery routes into one disk, each with its own verification story, is how the narrow mechanism becomes the general-purpose updater by accretion instead of by design.
- **If "daily driver" ships without it.** Existing VMs take integration fixes and freeze on everything else. Security backports, the graphics stack, and kernel updates reach only new installs, and the support answer for a two-month-old VM whose compositor stack needs to move is still "reset and lose your home directory." The architecture document says this in its own voice on main; shipping the claim anyway means the docs contradict the marketing.

### 2.3 Host-bridge reliability ("guest host-bridge hygiene")

- **Today.** Four virtio-serial bridges (small guest programs that talk to the Mac over a virtual serial channel) plus the console port plus the audio route directory carry the whole host-integration story (`macos/run-qemu-gpu.sh:1523-1582`): clipboard, audio, authentication, camera, and the console. They are guest-side long-running units, and one has a documented failure class. From the field write-up: `omarchy-native-audio-bridge` never unloads the remap modules left by a previous instance in PipeWire, the Linux audio server, so with `Restart=on-failure` restarting it 284 times the guest accumulated 8 duplicate copies of every host device and leaked 72 of 89 PipeWire modules, until `pipewire-pulse` sat at 1021 of 1024 file descriptors (the open-file handles a process is allowed); past that point `pactl load-module`, the command-line client for that audio server, retried at 1 Hz forever, producing 421,712 journal lines and roughly 86,000 `pactl` spawns per day on top of an already high polling baseline of 8 to 9 spawns per second (about 750,000 per day) in normal operation. The script is not owned by any pacman package. The positive example is the same shape solved: `omarchy-fcitx5.service` with `Restart=always` and `RestartSec=2`, no `fcitx5` binary present, produced 333,398 restarts in 9 days and 2,002,172 journal lines — 54% of the journal, 2.1 GB — because `RestartSec=2` sits exactly on systemd's default start-limit boundary so the rate limiter never engages. That one landed upstream as `e48f8382` and Try carried a downstream drop-in (#91 → #106, merged 2026-09-04). Two things changed this month: #193's integration manager is the delivery vehicle this class was missing, once its payloads widen past sudo Touch ID; and two fixes of exactly this shape landed on main — #184 recovers the guest clock after Mac sleep, #226 recovers the Cocoa full grab tap after macOS disables it. Neither is a feature; both are "the bridge did not survive something the host did to it", which is the class this row names.
- **Why it matters for daily-driver.** These are uptime-proportional failures. They are invisible in a 30-minute demo and unavoidable in a week. A daily driver by definition runs long enough to hit them, and the symptom the user sees is not "the audio bridge leaked modules" but "sound stopped working and the fans are on."
- **Candidate path.** Treat the bridges as a class with shared hygiene rules rather than fixing them one at a time: reclaim orphans at startup by deterministic name prefix (the remap modules already have derivable names); track what was loaded before loading more; bounded backoff plus a real `StartLimitIntervalSec`/`StartLimitBurst` pair chosen so it cannot sit on the default boundary the way `RestartSec=2` did; subscribe to PipeWire events instead of polling; raise `LimitNOFILE`, the ceiling on how many files a service may hold open, as a floor rather than a fix. A guest-side contract test that boots, restarts each bridge N times, and asserts that module and descriptor counts return to baseline would convert the class into CI, the automated checks that run on every change. Rate-limiting and a size cap in journald, the systemd log store, are cheap insurance against the 2.1 GB outcome regardless. The ordering consequence for 2.2 is direct: this class should be the first widened payload, because the fix and the delivery problem are the same problem and because these files are not owned by a package.
- **Owner.** Try for the bridges and their units; Omarchy upstream for anything that is really a systemd-unit-hygiene pattern (the fcitx5 fix went upstream, correctly).
- **Dependency.** 2.2 — until the integration manager carries host-bridge scripts and their units, a fixed bridge still reaches only new VMs, which is exactly what happened to the guest in the field write-up. #184 and #226 are on main and therefore reach a new factory; whether they reach an existing disk is 2.2's question.
- **Horizon.** 0.
- **Evidence anchors.** the author's unpublished field write-ups on the audio bridge and the fcitx5 restart loop; `docs/architecture.md:66-73` (clipboard bridge), `:75-82` (camera bridge); `macos/run-qemu-gpu.sh:1523-1582`. Also `README.md:129-137`, which already lists the shared folder and clipboard as "not yet verified" since the QEMU 11.1.1 port — the same hygiene question aimed at the other bridges. Also try-omarchy PR #184, PR #226 and PR #193.
- **Risk.** The failure is diagnosed on one guest lineage (a v0.3.0 factory) and the audio bridge may have changed since; that is a reason to re-run the check on a 0.4.x guest, not to assume it is fixed. The deeper risk is that this reads as a bug report rather than a class, and one leak gets patched while the pattern stays.
- **If "daily driver" ships without it.** The VM is livable for hours and unreliable for weeks, and the failures are hard for users to attribute — they surface as audio loss, disk pressure from journals, or general slowness. This is the row most likely to generate issues that read like unrelated flakiness.

### 2.4 aarch64 packaging: Try's part only

- **Today.** Try still builds and holds its own ABI island, but the reason has narrowed to one package. Hyprland, the Wayland compositor that is Omarchy's window manager, is "the one source-patched guest package" (`guest/README.md:31-36`), rebuilt with a guarded rounded-border patch for the VM graphics path; the factory on main now builds `aquamarine 0.15.1-1` "from a reviewed Arch-derived PKGBUILD and upstream tarball, then rebuilds Hyprtoolkit against its `libaquamarine.so=14` ABI, matching Hyprland 0.56.2", all three held on the guest's `IgnorePkg` never-upgrade list, the rationale recorded at `58cbac5` being that "mixing the newer mirror Hyprtoolkit with the older aquamarine cannot resolve" (`docs/architecture.md`, main; the same passage at `58cbac5` pinned `aquamarine 0.14.0-2` against `libaquamarine.so=13`, `docs/architecture.md:175-186`, `guest/pinned-packages/README.md`). Outside Try, the channel arrived. As of 2026-09-22 pkgs.omarchy.org serves stable, rc and edge aarch64 repositories and all three are live: stable and rc carry 21 packages each, mostly agent command-line tools (`claude-code`, `cursor-cli`, `openai-codex-bin`, `github-copilot-cli`, `crush-bin`), and edge carries 127, including `hyprland-0.56.2-3`, `hyprtoolkit-0.5.4-5.1`, `hyprland-guiutils-0.2.2-3`, `omarchy-4.0.2-1`, `omarchy-chromium` and `1password`. On no tier at all is aquamarine. So two of the three packages Try rebuilds are published at exactly the ABI Try now pins, and the library between them is not. Both package pull requests this row used to track are closed: omarchy-pkgs PR #240 on 2026-09-18 by ryanrhughes — "Closing in favour of smaller PRs: 11 of these 21 packages already have aarch64 on master" — and PR #223 on 2026-09-16, because the Snapdragon ISO consumes the published ARM repositories directly. omarchy-mac PR #345 (merged 2026-09-05) already pins its three Hyprland packages to signed official edge.
- **Why it matters for daily-driver.** Every package Try rebuilds is one Try must re-port on every Omarchy release, and the ABI pin is transitive: one held package drags two more. The factory just did that work again to move from `aquamarine 0.14.0-2` to `0.15.1-1`. The maintainer named the fix publicly on try-omarchy #57 — "ARM package compatibility is being worked on for Omarchy in general, will be fixed" and "Yes, this repo and PR: https://github.com/omacom/omarchy-pkgs/pull/240. It's not the only piece, but it's a big one." That pull request is now closed in favour of smaller ones, which changes who the conversation is with rather than retracting the point. The consequence of not converging is unchanged: `omarchy update` inside the guest keeps being a slightly different operation than `omarchy update` anywhere else.
- **Candidate path (Try's half, and only Try's half).** Three moves, and the second is now testable rather than aspirational. First, stop growing the island: treat a new source-patched or ABI-pinned guest package as a decision that needs a reason, not a default. Second, consume the published aarch64 channel where a signed package already exists — which for Hyprland and hyprtoolkit it now does, at the versions the factory pins — with the pin recipe in `guest/pinned-packages/README.md` retained as the documented fallback rather than the primary mechanism, and with aquamarine as the one package that recipe still has to build. Third, keep a small, honestly scoped Try package — guest tools and the host-bridge binaries — and get the overlay binaries in `/usr/local/bin` into it, so that pipe 2 has something package-shaped to deliver instead of loose files. One question Try cannot settle alone rides on the second move: which tier. Edge has the compositor stack; stable and rc do not. "Track the stable tier" and "stop rebuilding the packages Try rebuilds" are, today, incompatible instructions.
- **Owner.** Try for the three moves above. **The aarch64 package owners** for the channel's policy, which Try cannot do — and that is now a group rather than a person: omarchy-pkgs maintainers (ryanrhughes, who closed #240 in favour of per-package pull requests), Omarchy M's package owner, and Omarchy Dragon's, announced 2026-09-18 with Matt Gilg on aarch64 packages. Try consumes. Carried here as an external dependency, not a Try checkbox, and it should not appear on a Try milestone.
- **Dependency.** Try's half depends on nothing; the packages it would consume exist today. What remains external: aquamarine is not an omarchy-pkgs package at all; the channel's aarch64 Hyprland is version-gated against Arch Linux ARM's own aquamarine (omarchy-pkgs `pkgbuilds/hyprland/.omarchy/package.json`: `rebuilt_against` aarch64 `aquamarine 0.15.0-2`), one minor version behind the 0.15.1-1 Try rebuilds, so consuming edge's Hyprland means also consuming Arch Linux ARM's aquamarine and testing that ABI; and who carries or upstreams the rounded-border patch, which no channel Hyprland has.
- **Horizon.** 0 for Try's half. The external half is tracked, not gated.
- **Evidence anchors.** `guest/README.md:31-36`; `docs/architecture.md` (main) for the `aquamarine 0.15.1-1` / `libaquamarine.so=14` pin against Hyprland 0.56.2, and `docs/architecture.md:175-186` for what it was at `58cbac5`; `guest/pinned-packages/README.md`; try-omarchy #57; omarchy-pkgs #199 with the 2026-09-22 tier readings; omarchy-pkgs PR #240 (closed 2026-09-18); omarchy-pkgs PR #223 (closed 2026-09-16); omarchy-mac PR #345; omarchy-mac PR #354 (recovery for installs stranded before the ARM package sources policy — the failure mode of getting this wrong, already observed next door); [Introducing Omarchy Dragon](https://omarchy.org/news/2026/09/introducing-omarchy-dragon/).
- **Risk.** Converging too early strands the guest if the channel moves under it: omarchy-mac PR #354 exists precisely because installs got stranded across an ARM package sources policy change. The risk has sharpened rather than disappeared. Try's factory and edge now agree on Hyprland 0.56.2 and `libaquamarine.so=14`, so the switchover is cheap today and expensive the moment edge moves again — and edge is by definition the tier that moves, which is what makes the tier question a real one. The fallback recipe must stay real, and the switchover needs the guard behaviour pipe 2 is designing anyway.
- **If "daily driver" ships without it.** Try stays the compositor's distro. Every upstream Omarchy release is a re-port with a three-package ABI puzzle attached, the maintenance cost scales with Omarchy's release cadence rather than with Try's, and the aarch64 work happening one repository over does not reduce Try's load at all.

### 2.5 Chromium GPU process crash-loop on virgl (#230)

- **Today.** try-omarchy #230 (2026-09-18): Try Omarchy 0.4.0 build 5 on an Apple M5 Max under macOS 27.2, a beta, stock 8 vCPU / 8 GB configuration with virgl enabled. Opening any Chromium-family browser — `chromium 153.0.8010.36-1` from the image and `google-chrome 153.0.8010.47-1` from the AUR, "both affected" — makes the whole guest progressively unresponsive: laggy input, a spinning cursor, SSH no longer answering. Guest load average "spikes to **~16–22 on 8 vCPUs**", the kernel log fills with `virtio_net virtio0: NETDEV WATCHDOG: transmit queue 0 timed out` and with `drm_atomic_helper` vblank warnings, and one session ended with the journal daemon dumping core. The browser's own stderr names the mechanism: "eglCreateContext ES 3.0 failed with error EGL_BAD_ATTRIBUTE. ES version fallback is disabled." and then "Exiting GPU process due to errors during initialization", after which the GPU process respawns in a loop that pegs every core. A follow-up comment supplies the sharpest part, and it is a comparison rather than a log: the compositor hits the same wall and survives it, because aquamarine logs "eglCreateContext failed with GLES 3.2, retrying GLES 3.0" and then renders fine at an idle cost of 1 to 2 percent, while Chromium's ANGLE is refused even on its ES 3.0 attempt and has version fallback disabled. The reporter's workaround, `--use-angle=swiftshader`, is "fully stable (0 GPU process exits)" at a cost of "around 5 cores of software rendering" on media-heavy pages. The same report carries one host-side crash as well: a SIGSEGV in `qkbd_state_modifier_get` under `-[QemuCocoaView handleEventLocked:]`, which the reporter suggests is "Possibly the same as #213" and plausibly a keypress arriving while the guest is wedged.
- **Why it matters for daily-driver.** The browser is the daily-driver workload, not an accessory to it: documentation, the web half of every agentic loop, a meeting, a dashboard left open all day. A failure that begins when the user opens Chromium and ends with the entire guest unresponsive is not a graphics bug with a workaround, it is the machine being unusable for its main purpose. And the workaround inverts the point of the whole graphics chain: software rendering costing around five cores on a 14-vCPU guest is exactly what virgl exists to avoid, which is why "ship the flag" is an interim answer rather than a fix.
- **Candidate path.** Establish the operating system first. This report is on a macOS 27.2 beta and an M5 Max, a configuration nobody else in this document has; the first job is a reproduction on released macOS 27.0 or on 26, on hardware that already appears in the issue tracker. If it reproduces there, this is a Horizon 0 row beside 2.1, because it is the same shape of failure — the app runs and the workload does not. If it does not, it stays here as a tracked M5-or-beta observation. Either way the technical question is narrow and already located: why the host renderer answers Chromium's ES 3.0 context request with `EGL_BAD_ATTRIBUTE` while Chromium has "ES version fallback" disabled, when aquamarine on the same device asks for GLES 3.2, fails, retries at 3.0, and renders; the answer lives in the virglrenderer and ANGLE EGL attribute handling on the host, not in the guest browser packages.0. Shipping `--use-angle=swiftshader` in the image's browser flags is the reporter's own suggestion and a legitimate interim answer, provided it is recorded as a documented limitation rather than a resolution. Note where it would live: Omarchy's shipped `config/chromium-flags.conf` sets Wayland, password-store, and extension flags and nothing about the GPU, so the flag is a Try-side divergence from upstream's browser configuration and belongs in Try's overlay, delivered through the integration manager.
- **Owner.** Try for the host side of virglrenderer and for any default browser flags in the image; QEMU and virglrenderer upstream for the EGL and ANGLE context handling itself. Neither half is Omarchy upstream's, and the guest-side browser packages are not where the fix lives.
- **Dependency.** 2.1 for the operating-system question — reproducing on a released macOS is the same test-bed problem stated twice. Interacts with 4.1, because PR #168 carries a 5,595-line virglrenderer patch, so anything that changes host-side context handling meets that patch on the way in.
- **Horizon.** 0 if it reproduces on a released macOS; otherwise tracked here as the strongest candidate to promote.
- **Evidence anchors.** try-omarchy #230 and its 2026-09-18 follow-up comment; try-omarchy #213 (the possible overlap on the host crash); try-omarchy #217 / PR #225 (the man-db SIGTRAP the same reporter confirms and separates from this freeze); `guest/packages.txt:73`; `README.md:129-137` for the host graphics supply chain this lands in.
- **Risk.** Two. Reproduction may genuinely require an M5 or a 27.2 beta, in which case the row rests on evidence nobody on the project has, which is how a report that breaks the daily-driver workload stays open for a month. And the interim flag is sticky: an image that ships SwiftShader by default never gets hardware acceleration back unless somebody remembers to take the flag out after the host renderer is fixed.
- **If "daily driver" ships without it.** The headline workload freezes the machine, and the supported answer is "turn off GPU acceleration in your browser". That is a defensible v1 limitation if it is written down; discovered by the user at their desk, halfway through a working day, it reads as the VM being broken.

## 3. Horizon 1 (P1): fit on a 24 GB Mac next to macOS and Parallels

The architecture for this section is fixed and stated once: macOS is the home base, Windows runs in Parallels — the commercial Mac virtualization product — beside Try, and the two VMs are peers on the Mac. Nothing in this document proposes running Windows inside the Omarchy guest; Omarchy's own Windows story is nested Dockur-in-Docker-on-KVM — the Dockur project running Windows in a Docker container on KVM, the Linux hypervisor interface the guest would itself have to provide — with a 64 GB disk floor and no GPU passthrough (`omarchy manual/28-windows-vm.md`), which is the right design for a machine whose whole OS is Omarchy and a non-goal for a Mac-resident lane.

### 3.1 The memory envelope on 24 GB and smaller hosts

- **Today.** Memory return shipped. PR #243 (themartiano, merged 2026-09-22) attaches the balloon as `virtio-balloon-pci,free-page-reporting=on` and pairs it with a checksum-pinned HVF patch that handles each reported range in four steps: "Validate the complete range against the system memory map and host page size", remove its stage-2 mapping with `hv_vm_unmap`, "Replace the host backing at the same address with private anonymous demand-zero memory using `mmap(MAP_FIXED)`", then restore the mapping before acknowledging the report to Linux. The route is chosen deliberately against the obvious one: it "avoids Darwin's private `MADV_FREE_REUSABLE` advice and its persistent reusable-accounting state", at a stated cost of "host VM-map fragmentation and fault-in cost when memory is reused" (`docs/memory-reclamation.md`, main). Selected memory remains the guest's RAM capacity and the balloon is never inflated. The measured result, on Apple silicon under macOS 27.0 with a 3 GiB headless VM freeing 768 MiB three times, is "728.3, 742.3, and 718.3 MiB across the three cycles with reporting enabled" against "0.0, 0.0, and 0.2 MiB" for the same runtime with reporting off. It reaches existing VMs: the feature "needs an updated runtime and a VM restart, not a new guest disk". Unchanged around it: the start menu offers 4, 6, 8 and 12 GiB and then 4 GiB steps, always leaving 4 GiB for macOS (`README.md:344-362`), the picker added by PR #82 (rdtiv, merged 2026-09-09); try-omarchy #99 (closed) reported memory pressure on 8 GB Macs; #189 is about building the guest image on a 16 GB Mac, a different problem. The host-side numbers for the test bed are in the M4 Pro measurement notes and predate all of this.
- **Why it matters for daily-driver.** On a 24 GB machine the arithmetic is macOS plus an 8-to-16 GiB Omarchy guest plus a Parallels Windows VM, and there is no slack. The question a buyer asks is not "does it support ballooning", it is "can I keep both VMs open for a working day". That question now has a number behind it, but the number comes from a headless 3 GiB guest allocating and freeing in a loop on macOS 27.0 — no desktop, no compositor, no browser, and not the operating system most of the installed base runs. The distance between "reclaim works" and "the envelope is documented" is exactly the distance between that smoke test and the arithmetic above.
- **Candidate path.** Branch (a), memory return ships, is what happened, so what remains is validation and a written contract. #243 names its own remaining validation and that list is the gate — "macOS 26, desktop/graphics workloads, and sustained allocation churn have not been tested", plus EL2, unverified because "The test host does not support nested virtualization". Three things follow. Re-run the smoke test on macOS 26, including on the 24 GB M4 Pro test bed, which has never run 27. Measure a desktop workload rather than a synthetic one — compositor up, a browser open, a language server indexing — because file cache, fragmentation and graphics overhead are precisely what the documentation warns will keep pages resident, which is why "`selected RAM - guest used RAM` is not an exact prediction of macOS memory returned". Then publish the contract: the shipped picker plus a characterised Parallels coexistence envelope, which is 5.2 with a second consumer attached. ArcBox, a macOS virtualization project whose write-up is linked in the anchors below, remains the outside comparison, and its warning has turned from hypothesis into control group: a plain balloon without the host-side discard path is a "placebo" (guest starved, host footprint +0.2 MB), which is what #243's reporting-off run measured.
- **Owner.** Try for the balloon configuration, the pinned patch, the picker and the guidance; QEMU upstream for whether that reclaim path ever has a home other than a patch Try carries.
- **Dependency.** Validation rather than design. Note that the reclaim path unmaps and remaps through the same `hv_vm_unmap` surface as row 2.1's crash signature — a reason to read the desktop-workload validation and the 2.1 evidence together, not a reason to expect a new failure.
- **Horizon.** 1.
- **Evidence anchors.** `docs/memory-reclamation.md` (main); try-omarchy PR #243 for the measurements and the remaining-validation list; `macos/run-qemu-gpu.sh:1559` for the balloon line without `free-page-reporting` at `58cbac5`; `README.md:150-161`; try-omarchy PR #82; try-omarchy #189; [ArcBox: the macOS VM memory ratchet](https://arcbox.dev/blog/macos-vm-memory-ratchet); [apple/container technical overview](https://github.com/apple/container/blob/main/docs/technical-overview.md) — "memory pages freed to the Linux operating system by processes running in the container's VM are not relinquished to the host", which is the contrast on the Virtualization.framework (VZ) side and part of why Decision 4 of the executive briefing stays on HVF; M4 Pro measurement notes.
- **Risk.** The number is real and the envelope is not. Publishing "memory comes back" on the strength of a headless synthetic test is how a roadmap acquires a support thread: a desktop guest holds file cache, the compositor holds graphics allocations, and a user who reads 718 MiB and observes 100 will file a regression that is not one. The second risk sits under the feature rather than beside it — the reclaim path is a pinned patch to QEMU's HVF memory handling, launch refuses binaries without it, and it has no upstream home, so it joins the list of things Try maintains alone, and no proposal of the approach was found on qemu-devel; it is the one piece of Try's HVF work every macOS VMM would want, and upstreaming it is the way off that list.

### 3.2 Idle and background cost

- **Today.** The large win already landed: moving to QEMU 11.1.1 with Apple's in-hypervisor GICv3, the ARM standard interrupt controller now provided by the hypervisor rather than emulated by QEMU (PR #62, caius72, v0.3.0), took QEMU from roughly 65% of a core to roughly 15%, and `coreaudiod` from 6.4% to 0.3% (README). `-cpu host,pmu=off` is set because HVF provides no usable guest PMU, the CPU's performance monitoring unit whose counters profilers read (`macos/run-qemu-gpu.sh:1528`), which also means in-guest profiling tools will not help diagnose the remainder.
- **Why it matters for daily-driver.** Idle cost decides whether the VM stays open between uses or gets quit, and a VM that gets quit is not a daily driver. It interacts directly with 3.3: if quitting is expensive people stop doing it, and if staying open is expensive they stop doing that. #152's opt-in automatic startup changes the weighting rather than the measurement: with the VM starting when the Mac does, "leave it running" becomes the default posture instead of a choice, so the idle screensaver cost below is paid across the whole day by people who never decided to pay it.
- **Candidate path.** Establish the current baseline rather than optimise blind. Measured on the M4 Pro test bed: with the desktop idle, QEMU sits at 7 to 9 percent of one core with periodic spikes to about 17 percent and `coreaudiod` under 2.5 percent, consistent with the README figure; when Omarchy's screensaver starts after 150 s of idle (`omarchy config/omarchy/shell.json:4`), QEMU rises to 50 to 63 percent of a core and stays there. The idle screensaver is therefore the largest background cost on this stack, and the cheapest fix is a VM-aware idle policy (a still screensaver, a longer timeout, or none) in Try's overlay rather than anything in QEMU. Still to measure: the same with the audio bridge inactive, and with a Parallels VM also running. The remaining cost after GICv3 is most likely timer and display-cadence related rather than interrupt related, but that is a hypothesis, not a finding.
- **Owner.** Try; QEMU for anything in the HVF timer path.
- **Dependency.** None blocking; it is an input to 3.1 and to 5.2.
- **Horizon.** 1.
- **Evidence anchors.** try-omarchy PR #62; `README.md` idle-CPU figures; `macos/run-qemu-gpu.sh:1528`; M4 Pro measurement notes.
- **Risk.** Low. The failure mode is spending effort here because it is measurable, when the binding constraint is memory.

### 3.3 The clean shutdown and sleep story

- **Today.** Most of this row shipped, and what is left is narrower and sharper. #152 (drdator, merged 2026-09-21) added opt-in automatic startup; a "Try Omarchy Settings" entry reachable from inside Omarchy through Setup, search, or `omarchy-native-settings`; "Restart Try Omarchy…", which "asks Linux to shut down cleanly, then starts a new QEMU process with the saved settings"; and "Shut down to manage…", which keeps the native window open for VM location and reset. That clean path is code, not a promise: `shutDownForSettings` executes `system_powerdown` over the QMP session before relaunching (`macos/Sources/OmarchyVMHelper/VMApplicationController.swift`, main). try-omarchy #183 — the start menu unreachable after an in-guest shutdown, so Resources → Configure could not be opened — was closed by the maintainer on 2026-09-22: "This should be fixed on the next release, likely addressed by changes in #152." What did not change is the operation users perform most deliberately. Quitting the app still forwards `SIGTERM` (`applicationShouldTerminate` in the same file on main; `macos/run-qemu-gpu.sh:1077-1141` for the launcher's own terminate-then-kill after roughly 2 s), so the dialog try-omarchy #146 asks for is still open — "closing the VM currently powers off immediately (terminate) upon confirmation. Ideally, it would ask what you want to do (shutdown, suspend/pause, or terminate)… Shutdown should send a shutdown command to Omarchy" — and so is its second complaint, that "the launcher doesn't recognize that the VM is suspended" and that it is "impossible to unsuspend/resume". Host-sleep pause and resume over an authenticated QMP session is unchanged and still works across lid close (`docs/architecture.md:56-64`).
- **Why it matters for daily-driver.** Lid close, quit, and reopen are the three most frequent lifecycle operations on a laptop, performed dozens of times a week. Two of the three now have answers: lid close pauses and resumes, and the settings restart proves the clean shutdown path end to end. That makes the third conspicuous rather than merely unfinished — the one lifecycle event the user initiates on purpose, Cmd-Q, is the one that cuts power with a two-second grace period. Autostart raises the stakes: a VM that starts itself is a VM whose only deliberate lifecycle event is the quit.
- **Candidate path.** The remaining work is small and the transport is proven twice over. A quit dialog offering shutdown / pause / terminate, with shutdown issuing a guest power-button event (`system_powerdown`) over the existing QMP session and waiting on a bounded timeout before falling back to the current terminate path — not speculative, because `shutDownForSettings` already does exactly this for the restart flow, and because in both bounded launches recorded in the M4 Pro measurement notes the guest honored `system_powerdown` and QEMU exited about five seconds later. Then a visible paused state in the app, which is what removing the Cocoa Pause and Resume menu items in PR #101 left unlabelled and what #146 still reports. Documented, the supported sleep path is one sentence: close the lid, the guest pauses in memory and resumes on wake.
- **Owner.** Try, entirely.
- **Dependency.** None technically, and one consumer downstream: 3.5's app self-update needs the clean-shutdown guarantee this row would supply, because `docs/app-updates.md` says so in as many words. Note that #146's *third* ask — that "'Pause' … does not actually store a state/memory snapshot" — is a different feature and is deliberately 6.7, Horizon 2, because it needs save-to-disk.
- **Horizon.** 1.
- **Evidence anchors.** try-omarchy PR #152; `macos/Sources/OmarchyVMHelper/VMApplicationController.swift` (main) for `shutDownForSettings` and for `applicationShouldTerminate`; `README.md` (main) for the user-facing wording of automatic startup, Try Omarchy Settings, Restart Try Omarchy… and Shut down to manage…; `macos/run-qemu-gpu.sh:1077-1141`; try-omarchy #146; try-omarchy PR #101; `docs/architecture.md:56-64`; try-omarchy #183, closed 2026-09-22; M4 Pro measurement notes.
- **Risk.** A guest that refuses to shut down cleanly (a hung unit, an unsaved editor) must not hang the app; the timeout-and-fall-back behaviour is the whole design, and getting it wrong replaces an abrupt quit with a stuck one, which is worse. The new risk is procedural: #183 was closed on inference, not reproduction — the maintainer could not reproduce it and closed it as likely addressed by #152 — so if it survives, it returns as a new report rather than as a regression against a known one.

### 3.4 Disk capacity, Time Machine exclusion and APFS clone snapshots

- **Today.** The capacity half shipped and the recovery half did not. #246 (themartiano, merged 2026-09-22) puts a maximum disk capacity beside CPU and RAM in Resources: new launcher settings default to 64 GiB, a larger capacity is applied to the stopped VM on its next launch, "APFS allocates host storage as the guest writes data, and the guest expands ext4 on boot", existing disks never shrink, blank values preserve the current capacity, and it closes #104, #132 and #244. `macos/resize-vm-disk.sh` is therefore no longer the user path. The layout underneath is unchanged: the workspace lives at `~/Library/Application Support/Try Omarchy/VM/v1` and the disk is a raw image holding the Linux ext4 filesystem, sparse (it occupies only the blocks actually written), and cloned with `cp -c`, the APFS copy-on-write clone operation, where cloning happens at all (`docs/architecture.md:233-236`, `:192-225`). There is still no Time Machine exclusion. And try-omarchy #92 (vzxxbacq) is still open with no maintainer reply, still proposing the right primitive: "Each snapshot is an APFS copy-on-write clone of the entire VM `rootfs.ext4`. Online creation briefly freezes the guest filesystem and pauses QEMU to ensure consistency, then immediately resumes the VM." The author is explicit about the limits — restore rolls back the whole disk including `/home`, RAM is not saved, and snapshots live on the same volume so they are not backups — and says a prototype exists.
- **Why it matters for daily-driver.** Two separate things go wrong without this. Time Machine, macOS's built-in backup system, will happily back up a multi-gigabyte raw disk image that changes constantly, which wrecks backup performance for the whole Mac — and a 64 GiB default makes the object it misunderstands larger, even though the file stays sparse. And a daily driver eventually needs "undo": the guest's own answer is Snapper plus Limine, the Linux snapshot tool and the bootloader that offers those snapshots at startup (`omarchy manual/47-system-snapshots.md`), which cannot work here because Try boots the kernel directly with no bootloader — a Limine boot menu has nowhere to appear. That #246 closed three disk-size issues at once is a fair measure of how often the first thing people run out of is room.
- **Candidate path.** Exclusion is small, independent, and now slightly more valuable than it was: mark the workspace with the standard exclusion attribute at creation and document it. Snapshots are #92, and the pause-freeze-clone-resume sequence it describes composes with the QMP control session already in place for host sleep and with the workspace lock #246 now takes before touching a disk. The honest framing in the UI matters as much as the mechanism: these are rollback points on the same volume, not backups, and restoring one takes `/home` with it.
- **Owner.** Try.
- **Dependency.** External-drive workspaces are already APFS-only, which is the same constraint clone snapshots need. Interacts with 6.9 (DiskImageKit's layered ASIF disk images, which are now on a released macOS 27), which may eventually be a better substrate for the same feature.
- **Horizon.** 1.
- **Evidence anchors.** try-omarchy PR #246, which closes #104, #132 and #244; `docs/architecture.md` (main) for the configurable capacity and its 64 GiB default; `macos/resize-vm-disk.sh` as the superseded path; try-omarchy #92; `docs/architecture.md:192-225`; `omarchy manual/47-system-snapshots.md`; `docs/architecture.md:56-64`.
- **Risk.** Clone snapshots invite the mental model "this is my backup", which they are not. Second, whole-disk rollback including `/home` is a sharp edge for anyone who snapshots before an update and then works for an hour. Third, an open prototype with no maintainer response is a contributor-retention question as much as a technical one, and it got worse this month: the disk area around #92 shipped twice while #92 itself went another week unanswered — **your call** whether it gets a direction reply.

### 3.5 App self-update (#232, #234)

- **Today.** The notification stage shipped; the installing stage is designed and unbuilt. PR #234 added version display, a manual **Check for Updates…**, and an opt-in check on app startup "limited to one attempt per 24 hours", run against GitHub's public releases endpoint for the repository and accepting "published, non-prerelease `vX.Y.Z` tags with an uploaded `TryOmarchy.dmg`". The checks "never invoke VM shutdown, app replacement, or an installer"; the download action opens the release page so the user reads the notes themselves. `docs/app-updates.md` is explicit about what this is not: "Use [Sparkle 2](https://sparkle-project.org/documentation/) for signed downloads, verification, replacement, and relaunch. The release checker is an interim notification feature, not a second installation mechanism." It then lists what installation needs first — a stable HTTPS appcast location and an Ed25519 signing key whose public half alone is embedded in the app; monotonically increasing build numbers across release branches; signing and notarizing the app and the update archive before the appcast is published; and gating installation on the QEMU supervisor, because "The current app termination path forwards SIGTERM, so simply letting Sparkle terminate the app is not a clean-shutdown guarantee". One prerequisite is a versioning dependency rather than a design choice: accurate comparisons need `TryOmarchyBuildDescribe` to "exactly equal `v` followed by `CFBundleShortVersionString`", delivered by try-omarchy PR #223 (merged 2026-09-21) — and #250 is the field example of its absence, a bundle installed from the v0.4.1 DMG that reports `CFBundleShortVersionString 0.4.0`. try-omarchy #232 stays open until the signed installation flow and its acceptance checks are complete.
- **Why it matters for daily-driver.** On this project the Mac app is not a shell around the interesting part; it *is* the QEMU build, the HVF patches, the launcher lifecycle and the integration bundles. "Two releases behind" therefore means two releases behind on the memory-reclaim patch and on whatever fixes the macOS 27 launch. It is also pipe 2's carrier: #193's bundles and #243's runtime both arrive with a new app, so a user who does not update the app does not update the VM either, no matter how good the in-guest channel gets.
- **Candidate path.** None invented here; the design note is the plan. What this row adds is sequencing and one honest alternative. The Sparkle prerequisite list contains exactly one item that is not Sparkle's problem — a clean-shutdown guarantee at app termination — and that is 3.3's remaining work, so the two belong in that order rather than in parallel. The version-stamping agreement from try-omarchy PR #223 is a precondition for the checker being correct at all, since without it the checker "cannot identify the installed release and never reports it as up to date". And the honest alternative: the interim checker, declared sufficient for v1 in the readiness document, is a pass. Silence about which of the two v1 means is not.
- **Owner.** Try.
- **Dependency.** 3.3 for the clean-shutdown guarantee. Version stamping (try-omarchy PR #223, xavierforge) merged on 2026-09-21; `docs/app-updates.md` on main still calls it proposed and is stale on that point.
- **Horizon.** 1.
- **Evidence anchors.** `docs/app-updates.md` (main); try-omarchy #232; try-omarchy PR #234; try-omarchy PR #223; try-omarchy #250 for the version-stamping symptom observed in the field.
- **Risk.** Running two automatic checkers is the named failure mode — the documentation says that when Sparkle ships it should replace the GitHub transport and migrate the user's opt-in preference, not run beside it. The second risk is operational: an Ed25519 update key is a new long-lived secret belonging to whoever cuts releases, and an update channel is the highest-value thing in the project to compromise.

### 4.1 Video decode: track the in-flight work, do not propose a second design

- **Today.** `README.md:28` states the limitation plainly: "Video decoding is CPU-only, so playback can be slow, especially at high resolutions. An improved video path is in development." try-omarchy #167 (nocell, 2026-09-08, open, no comments) describes a guest driver for VA-API, Linux's hardware video acceleration interface, plus a video-group broker feeding a host helper built on VideoToolbox, Apple's hardware video decoder, with decoded frames (IOSurfaces, the macOS buffers that can be shared between processes) reaching QEMU over a private Mach capability — a macOS handle for inter-process access — and a pinned FFmpeg for mpv and Firefox. PR #168 is the implementation: 75 files, +12,975/−50 as of 7f3ce66, `NativeVideoBridge.swift` and friends, QEMU patches (native-video-shmem, cocoa-hdr, display-cadence), a 5,595-line macOS 1.0.33 patch to virglrenderer (the host-side component that replays the guest's OpenGL), the guest VA-API driver and broker under `guest/video/`, HDR (high dynamic range) guest patches, and `docs/native-video.md` plus `docs/native-hdr.md`. GitHub reports its merge state as CONFLICTING — it no longer applies cleanly — with the CI "Test" check success and no formal reviews. Fail-Safe tested it on an M3 Max on 2026-09-12 and reported that "the hardware decoder bridge works across the tested codecs, the HDR guest/presenter path initializes, and native Wayland presentation feedback reaches approximately 120 fps", with guest CPU roughly 83-88% lower than software decode and 7 dropped frames in a 4 s clip — and also that "End-to-end color accuracy remains unverified", with audio continuity, Firefox, a controlled 60 Hz run, soak tests and HDR correctness outstanding, two build fixes needed, and a follow-up HDR highlight discrepancy of guest 63.7 fc against host 90.1 fc — foot-candles, a unit of light intensity — about 0.50 stops, cause not isolated. On 2026-09-21 the maintainer engaged with it for the first time: "Very promising indeed!", "Works on my M2 Pro.", "What do we need to make this production-ready?" — with two specific asks attached, querying the underlying hardware for the formats it actually supports rather than assuming them, and checking Firefox's habit of disabling a decoder permanently after two failures — and "I've pushed some changes to fix build and merged main." Six commits landed that day, among them "Merge main into native video support". The merge state is still CONFLICTING afterwards. On 2026-09-22 Fail-Safe, who did the physical testing, stepped back for the moment: "I'll try to circle back around to this sometime soon. Life has been getting in the way of fun as of late."
- **Why it matters for daily-driver.** Video is not a niche workload on a machine someone lives in: it is documentation, conference talks, screen shares, and a YouTube tab. CPU-only decode at 4K also collides directly with 3.1 and 3.2, since it spends the same cores and thermal budget the rest of the desktop needs.
- **Candidate path.** None proposed here on purpose. The design exists, it is under review, and a second design would be noise. What this row adds is the gate wording: for v1, this is either **landed**, or **explicitly deferred with the evidence recorded** — the 120 fps presentation figure and the 83-88% CPU reduction on one M3 Max are a promising physical test, not a shipped feature, and the unverified colour accuracy is a named open item, not a rounding error. A 120 fps presentation number is also not a GPU strategy; this path is VideoToolbox host decode, not Vulkan (the modern low-level graphics API) and not 3D, and it should not be described as one.
- **Owner.** Try, and the ownership is now clearer than it was: nocell's PR, Fail-Safe's physical testing, and the maintainer driving it since 2026-09-21; QEMU and virglrenderer for the vendored patches, which is a maintenance surface of its own given the 5,595-line virglrenderer patch.
- **Dependency.** The CONFLICTING merge state against a tree that has moved through v0.4.1 and then through twenty-nine more pull requests; the maintainer's own merge of main on 2026-09-21 did not clear it. Nothing in this document blocks it. Note the collision with 2.5: both this PR and any fix for #230 land in host-side virglrenderer.
- **Horizon.** 1, as a tracked gate.
- **Evidence anchors.** `README.md:28`; try-omarchy #167; try-omarchy PR #168 and Fail-Safe's 2026-09-12 review; `guest/packages.txt:73` (the only Vulkan ICD — installable client driver — in the guest today is `vulkan-swrast`, a software-only renderer, which is the baseline this is measured against).
- **Risk.** Size and vendoring. A 75-file PR that patches QEMU, virglrenderer and the guest simultaneously is hard to review incrementally and hard to rebase, and the vendored virglrenderer patch joins an existing supply-chain concern (`README.md:41-43`, `macos/build-qemu-gpu-runtime.sh:107-132`: the runtime bottles, the prebuilt binaries the host graphics stack is assembled from, come from Homebrew taps unmaintained since 2026-01-14). Deferring is a legitimate outcome; deferring silently is not.

### 4.2 Shared-folder throughput and the 9p-versus-virtiofs decision

- **Today.** One optional share, exported over virtio-9p with `security_model=none` so host operations run as the Mac user, with a custom QEMU patch adding `guest_owner_uid`/`guest_owner_gid` so the guest's permission checks agree with what the host will allow, mounted at `/mnt/mac` before the display manager starts and linked to `~/<folder name>` at login (`docs/architecture.md:114-122`). The test bed shares a host source directory. Throughput numbers: see M4 Pro measurement notes. `README.md:129-137` also lists the shared folder as not yet exercised since the QEMU 11.1.1 port. One related bug sits at the NAT layer rather than in the share, and belongs in the same conversation because the agentic loop is what holds those connections open: try-omarchy #238 (2026-09-20) reports that port forwarding prevents a restart while the previous TCP connections are still tearing down, so the app refuses to launch with “Mac TCP port 60443 isn’t available. Another app may already be using it.” while `netstat` shows nothing but `FIN_WAIT_2`, `CLOSE_WAIT` and `TIME_WAIT`. The user-visible symptom is "I cannot restart my VM", which puts it beside 3.3 as much as here.
- **Why it matters for daily-driver.** This is the agentic-coding filesystem. A coding agent walking a repository, `git status` on a large tree, `node_modules`, `cargo`/`rustc` incremental output, and a language server — the background process an editor uses for completion and diagnostics — indexing all hammer metadata operations, which is exactly where 9p is weakest. If the share is slow, the workaround users find is to stop using it, keeping everything inside the guest disk, and the "Mac stays home base" premise quietly stops being true.
- **Candidate path.** Measure first: sequential read/write and, more importantly, metadata-heavy operations (a large `git status`, a recursive stat walk) over 9p versus the same tree on the guest's own ext4. If 9p is adequate, document it and move on. If it is not, virtiofs is not the comparison, because it cannot run on this host: the reference virtiofsd depends on the rust-vmm `vhost` crate, which does not build on macOS (rust-vmm/vhost #110, open since 2022 with no activity), and Apple's own VirtioFS lives inside Virtualization.framework only; UTM and Lima both use 9p for their QEMU backends on macOS. The real alternatives are 9p tuning (msize, cache mode, guest mount options) or a Try-written host daemon, which is a project in itself and carries a different security posture and uid-mapping story than the `security_model=none` plus remap-patch arrangement that exists today. Three smaller items belong in the same row. #238's listener is neither released nor retried, so the fix is to release or recreate it and retry across the teardown states. iCloud Drive over 9p is a footgun — evicted files, `.icloud` placeholders, and a daemon that materialises files behind the guest's back — and the documentation should say so. And multiple shares are a product choice about convenience, not a substitute for a fast share.
- **Owner.** Try; QEMU if the answer is virtiofs or 9p tuning (msize, cache mode) below the app.
- **Dependency.** Measurement. **Your call** on whether this is a v1 gate or a v1 documented limit.
- **Horizon.** 1 for the decision; the implementation lands wherever the numbers put it.
- **Evidence anchors.** `docs/architecture.md:114-122`; `README.md:129-137`; try-omarchy #238; M4 Pro measurement notes.
- **Risk.** Switching transports changes the security model paragraph in section 0 — the current arrangement's property is that every host file operation runs as the Mac user with real modes preserved, and any replacement has to state its own equivalent. Switching also breaks the `~/<folder name>` path convention if not done carefully, which is user-visible in every shell history.

### 4.3 The agentic coding loop

- **Today.** The strongest part of the story, and almost entirely inherited. Omarchy ships 13 agent command-line tools as stubs under mise, the toolchain manager it installs them through (`omarchy manual/17-ai.md:5-19`), a default-agent picker, an agents usage panel, crash-to-agent via `systemd-coredump`, the Omarchy skill symlinked into `~/.claude/skills` and equivalents, `omarchy-nvim`, Docker and compose, mise toolchains, `gh`, and `lazygit` — all architecture-neutral, which is why it works unchanged on aarch64. Omarchy also ships a passwordless sudo mode described for the case where "an AI agent is doing a long stretch of system work for you" (`omarchy manual/48-security.md`). On the Try side, the SSH preset (`tcp:2222:22`) adds `tryomarchy.ssh_access=1` to the kernel command line and a systemd generator enables `sshd` for that boot only (`docs/architecture.md:130-136`), which is what VS Code Remote and any host-side agent need. The known hole is `cursor-bin`: an install target in the AUR, the Arch User Repository of community build recipes, that the aarch64-refusal backport blocks, so the CLI agents are the path and Cursor.app is not. The channel reading in 2.4 is outside evidence for that sentence: the stable tier's 21 packages are mostly these same agent CLIs, and the one desktop editor among them is still the one Try's backport makes refuse cleanly. And Ghostty is installable on ARM64 as of try-omarchy PR #240 (MatthewFeroz, merged 2026-09-22), built from pinned source inside the guest with a wrapper that "enables software OpenGL only for the exact `omarchy.qemu_virgl=1` kernel option" — a VirGL compatibility fallback, explicitly "not a general VM graphics performance improvement", and the terminal half of this workload.
- **Why it matters for daily-driver.** For the persona this lane exists for, this *is* the workload. Everything else in the document is infrastructure under it.
- **Candidate path.** Mostly documentation and defaults rather than new code. Make the SSH preset discoverable as "this is how you attach VS Code Remote" rather than a port-forwarding entry. Say plainly where secrets live and cross what boundary: a `.env` on the 9p share is readable by the Mac user and by anything running as that user on macOS, which is a feature for convenience and a consideration for agents with shell access; 1Password's ARM64 build, installed from Omarchy's own repository, is the better answer. Note the sharp edge where passwordless sudo mode meets an agent with SSH access into the guest. And scope nested Docker honestly: `/dev/kvm` in the guest exists only on M3 and newer with macOS 26 or newer (`README.md:364-374`, `docs/architecture.md:39-48`), it is for **Linux** workloads such as devcontainers (development environments defined as containers) and KVM-backed tooling, and it must never be a v1 gate, because gating on it would exclude M1 and M2 owners, who are an official hardware class.
- **Owner.** Omarchy upstream owns the agent surface; Try owns the SSH preset, the share, and the documentation that connects them.
- **Dependency.** 4.2 — a slow share degrades every agent loop that touches host files.
- **Horizon.** 1 for the documentation; nothing here needs new mechanism.
- **Evidence anchors.** `omarchy manual/17-ai.md:5-19`; `omarchy manual/48-security.md`; `docs/architecture.md:130-136`; `README.md:364-374`; `docs/architecture.md:39-48`; `guest/spec.json:239-466` (the backports that make x86-only installers refuse cleanly on aarch64 instead of failing obscurely).
- **Risk.** The combination of passwordless sudo, an SSH-reachable guest, and a share that maps to the Mac user's real home directory is a coherent set of individually reasonable choices whose union deserves one paragraph of documentation. Writing that paragraph is the work.

### 4.4 Input and locale: shipped, with two threads and two new reports remaining

- **Evidence anchors.** try-omarchy #175 / PR #188; PR #190; PR #195; PR #239, all merged 2026-09-21; #181; #194; try-omarchy #222; try-omarchy #212; `macos/run-qemu-gpu.sh:1523-1582`; `docs/pinch-zoom.md`.

The new risk is reading #222 as a niche remote-control complaint: it is a general statement about injected events, so accessibility tools, automation and screen-sharing software all reach the same code path.

## 5. Horizon 1 (P3): Mac-resident table stakes

These are not "nice to have later". They are the things a Mac owner assumes work because everything else on their Mac does. If v1 cannot carry them, v1 should say so in one explicit sentence rather than leaving the reader to discover it.

### 5.1 Multi-monitor and scaling

- **Today.** Single output, by construction: the guest's virtual graphics card `virtio-gpu-gl-pci` is configured with `max_outputs=1`, meaning one display (`macos/run-qemu-gpu.sh:179`), and a Cocoa patch forwards the backing-pixel size and refresh rate through the virtual GPU's EDID — the data block a real monitor uses to announce its size and refresh rate — so the guest resizes and rescales with the window (`macos/patches/qemu-cocoa-dynamic-display.patch`); the guest keeps Hyprland's auto monitor rule (`guest/fragments/hypr-monitors-arm-qemu.append.lua`). HiDPI, Retina-style display scaling, works within that one window. The only movement since 0.4.1 is #179's display resync. `README.md:129-137` lists "Window resize across a HiDPI boundary" and "Mac output-device switching mid-session" as not yet verified since the port.
- **Why it matters for daily-driver.** Desk setups have two or three displays. A tiling window manager is precisely the kind of software people buy a second monitor for. "HiDPI works" is not "daily-driver display" — dragging the window to a different-scale display mid-session is the common case, and it is on the unverified list.
- **Candidate path.** Two steps that are separable. Verify and fix the single-window cases first, because they are already suspect: HiDPI-boundary resize and output-device switching mid-session. Then multi-output, which means raising `max_outputs`, extending the Cocoa dynamic-display patch to publish more than one EDID, and deciding the window model — one window per guest output is the conventional answer and interacts with the resizing patch that exists. One constraint this row must state: UTM's tracker records that QEMU supports only one GPU-accelerated display at a time (utmapp/UTM #6929), and UTM's multi-display support is one AppKit window per additional non-accelerated output. Multi-output on Try therefore means either one accelerated display plus software-rendered extras, or new work inside QEMU's virtio-gpu-gl and Cocoa code that nobody has done.
- **Owner.** Try; QEMU for the Cocoa display backend if the patch grows past what is comfortable to carry downstream.
- **Dependency.** Interacts with PR #168's display-cadence patch, which touches the same presentation path.
- **Horizon.** 1, or the explicit statement in 5.3.
- **Evidence anchors.** `macos/run-qemu-gpu.sh:1523-1582`; `macos/patches/qemu-cocoa-dynamic-display.patch`; `guest/fragments/hypr-monitors-arm-qemu.append.lua`; `README.md:129-137`.
- **Risk.** Multi-output on virtio-gpu-gl through virglrenderer and ANGLE — the layer that turns the replayed OpenGL ES into Apple's Metal — is not a flag flip; it is more surface in the exact layer where the vendored-patch burden already lives.

### 5.2 Parallels coexistence envelope

- **Today.** Still uncharacterised, with one lever and one stability fix added. The shipped facts around it: port forwards are loopback-only NAT with at most 32 rules (`macos/qemu-port-forwarding.sh`); bridged networking is an opt-in through a privileged `socket_vmnet` SMAppService daemon with one bridged session per Mac (`README.md:236-237`); the memory picker and the vCPU count are the resource levers (`README.md:150-161, 344-362`), joined on main by #246's maximum disk capacity. try-omarchy PR #209 is no longer open — it merged on 2026-09-21 and gives each VM a stable bridged MAC that survives app updates, disk replacement, resizing, resets and moves of the complete data folder, with **Copy MAC** and **Generate new MAC…** in the networking sheet and an explicit warning about the DHCP-reservation impact before regenerating. That lands squarely in this row: the person running two VMs beside macOS is exactly the person with DHCP reservations and firewall rules keyed to an address.
- **Why it matters for daily-driver.** For anyone whose business applications are Windows-only, this is not an edge case, it is the configuration. The question is whether both VMs can stay open across a working day, which is a Mac-side question about RAM, networking, disk and sleep — not a nesting question; section 3's opening states the non-goal.
- **Candidate path.** Characterise rather than engineer. Memory: what the 8/16 GiB picker leaves for a Parallels VM on a 24 GB host, which is 3.1's measurement with a second consumer — and which now turns on 3.1's *validation* rather than on whether reclaim exists at all, because freed guest memory returning to macOS changes this arithmetic in the Mac-resident's favour and nobody has measured by how much under a desktop load. Networking: whether both can reach each other, which for most real uses they can already — Tailscale, a userspace mesh VPN, needs no bridging, so a Mac, an Omarchy guest and a Windows VM on one tailnet is the low-friction answer that requires nothing new. Note the known interaction class: virtualization apps that install DHCP or NAT helpers can affect each other's Wi-Fi networking, which is worth a documented compatibility note. Disk: two multi-gigabyte images plus the Time Machine question in 3.4. Sleep: Try pauses over QMP on lid close (`docs/architecture.md:56-64`); what Parallels does is Parallels' business, but the combined wake behaviour is what the user experiences. Bridged networking is a **candidate**, not a requirement: taking it updates the security-model paragraph in section 0, and it is neither a v1 gate nor a Horizon 2 taboo — it already ships as an opt-in.
- **Owner.** Try for the documentation and any resource-lever changes. Apple for `vmnet` behaviour.
- **Dependency.** 3.1, and specifically its validation rather than its existence.
- **Horizon.** 1, or the explicit statement in 5.3.
- **Evidence anchors.** `macos/qemu-port-forwarding.sh`; `README.md:236-237`; try-omarchy PR #209 (merged 2026-09-21); try-omarchy PR #246; `README.md:150-161, 344-362`; `docs/architecture.md:56-64`; `omarchy manual/28-windows-vm.md` (named as the non-goal); M4 Pro measurement notes.
- **Risk.** Characterising a third-party product's behaviour ages badly across its releases; the envelope should be written as "what Try needs" rather than "what Parallels does".

### 5.3 The alternative: say it explicitly

- **Today.** 5.1 and 5.2 are undecided, and no readiness document states either limit.
- **Why it matters for daily-driver.** Stating a limit is a supported configuration; not stating it is a bug report queue.
- **Candidate path.** If 5.1 and 5.2 do not fit in v1, the honest version is a single sentence in the readiness document — something of the form *v1 targets a single display and loopback-only networking; multi-monitor and characterised coexistence with other virtualization apps are post-v1* — rather than silence. This is the cheapest row in the document and it is entirely **your call**.
- **Owner.** Try; the sentence goes in the readiness document.
- **Dependency.** 5.1 and 5.2 being decided either way.
- **Horizon.** 1.
- **Evidence anchors.** Doc A, Decision 5, last gate.
- **Risk.** Low. The failure mode is leaving the sentence out and letting readers discover the limits themselves.

## 6. Horizon 2

Named so they are visibly not v1. Each gets the shortest honest statement of what it would take. One framing note for the macOS 27 items below: macOS 27.0 was released on 2026-09-14, so custom Virtio devices for Linux guests, USB through Accessory Access, and DiskImageKit's layered sparse images are shipped operating-system capabilities now rather than announced ones. That changes when they can be evaluated, not whether they belong in v1 — none of them gives a Linux guest a GPU, and none of them is a rewrite trigger.

**6.1 Venus / KosmicKrisp / 16 KiB Mesa.** Today the chain is guest Mesa virgl → virtio-gpu-gl → virglrenderer → ANGLE → Metal — the guest's OpenGL leaving the Mesa graphics stack's virgl driver, crossing the virtual GPU, and being replayed and translated on the Mac — and the only Vulkan ICD in the guest is `vulkan-swrast` (`guest/packages.txt:73`); the README is explicit that KosmicKrisp "is not part of this path" (`README.md:129-131`). KosmicKrisp, an implementation of Vulkan on top of Metal, is Vulkan 1.3 conformant on Metal 4, Apple silicon only, with 1.4 coming ([LunarG](https://www.lunarg.com/lunarg-achieves-vulkan-1-3-conformance-with-kosmickrisp-on-apple-silicon/)). Venus over virtio-gpu — Venus being the protocol that carries Vulkan across the virtual GPU device — on macOS hosts exists in community QEMU forks, but "Apple Silicon Venus requires a patched guest Mesa ICD" for 16 KiB host pages, Apple silicon's page size where most Linux software assumes 4 KiB ([milesbuckton/homebrew-qemu-virgl](https://github.com/milesbuckton/homebrew-qemu-virgl)). Crucially this is not a compositor story: Hyprland has no Vulkan renderer ([Hyprland #1396](https://github.com/hyprwm/Hyprland/issues/1396)), so Venus would serve applications, video and ML, and compositor work stays in the virgl world — which is also why the rounded-border source patch exists. Owner: QEMU/Mesa upstream, with Try consuming. Horizon 2 unless evidence says otherwise.

**6.2 UEFI.** Direct kernel boot is load-bearing: it is why paired boot kits work, and it is why Limine, Snapper, UEFI secure boot and the macOS EFI story do not apply here. The proposed position is explicit: stay direct-boot through v1, revisit later (a second trigger now exists: omarchy-pkgs PR #591's `linux-aurora` kernel, if it assumes EFI) — and the specific trigger to revisit is if Shun Li's generic ARM64 VM images assume UEFI, because then Try either boots them as-is or keeps building its own factory. Owner: Try, with Omarchy M as the trigger. Anchors: `guest/spec.json:535`; `docs/architecture.md:192-225`; `omarchy manual/47-system-snapshots.md`.

**6.3 USB and Accessory Access.** macOS 27 adds USB passthrough for VMs via Accessory Access, its user-approved device framework, with user-controlled attach/detach and a "Claim USB Accessory" capability (WWDC26 session 224, an Apple developer-conference talk). This is a security surface, not a convenience checkbox: it changes the section 0 model materially. It is also no longer prospective: the framework is on a released macOS, so the security review is schedulable rather than hypothetical. Owner: Apple, then Try.

**6.4 Keychain, passkeys, login Touch ID, Bluetooth.** Today's Touch ID is sudo-only and the maintainer has said so publicly on try-omarchy #133: the merged PR #143 "does not expose Apple Passwords/Keychain, implement browser passkeys, or replace guest login/screen-unlock authentication", and the issue stays open for the requested integration. try-omarchy #191 is the adjacent hole: guest Chromium passkeys lack the phone/QR cross-device option because there is no Bluetooth in the guest at all — `/sys/class/bluetooth` absent, bluez not installed. Each is a distinct mechanism, and none is a small extension of the existing authentication bridge. Owner: Try, Horizon 2.

**6.5 Omarchy Link, for the record.** Issues #108, #114, #118, #122, #127 and #128 were opened and closed within minutes on 2026-09-04 by the same author, who wrote that "issues #108 through #130 were opened in this repository by mistake during an automated issue-publishing workflow." Never implemented, no code in tree, not a maintainer decision. They are mentioned here only so nobody cites them as a roadmap.

**6.6 FEX.** x86-64 usermode emulation on ARM64 Linux with monthly releases, needing an x86-64 rootfs, a full set of x86-64 system libraries installed alongside the ARM ones ([FEX-Emu](https://fex-emu.com/)); not packaged in Try. omarchy-pkgs merged `omarchy-steam-fex` for Apple silicon on 2026-09-20 (PR #470), so FEX itself is now in the shared channel for one use case. It is the only general answer to the unavailable-x86-app list, which is a product boundary rather than a bug list: the aarch64-refusal backports in `guest/spec.json:239-466` already make those installers fail clearly instead of obscurely. Owner: Omarchy M / omarchy-pkgs if anyone.

**6.7 Multi-VM and guest suspend-to-disk.** try-omarchy #145 asks for "multiple instances … A profile / session picker would be great"; today there is one workspace and the multi-disk switch is development-only. Suspend-to-disk is #146's third ask, which 3.3 defers here, and it is a genuinely hard row. The disk is raw ext4, so QEMU internal snapshots (which need QEMU's own qcow2 disk format) are unavailable; a state save would be QEMU's `migrate` command writing memory state to a file, paired with an APFS clone of the disk. QEMU 11.1.1 does carry `vmstate_gicv3_hvf` in `hw/intc/arm_gicv3_hvf.c` with `hv_gic_state_get_data` on save and `hv_gic_set_state` on load, and there is no migration blocker in the GIC or the HVF backend — but whether `savevm` or `migrate`-to-file (QEMU's two ways of writing a running VM's state out) works end to end on this stack is **unverified** (two concrete blockers are now known upstream: a snapshot-load assertion in `target/arm/machine.c` from HVF's cpreg pre-allocation, and a dirty-page-logging crash during migration on multi-GB guests, with a two-patch fix series posted to qemu-devel in April 2026 whose merge status is unconfirmed; UTM also documents that its own suspend excludes GPU-accelerated display devices), and the HVF series cover letter carries a caveat that survives any implementation: "Save states are incompatible between kernel-irqchip=on and off on HVF due to opaque vGIC state." Since the nested-virtualization probe path selects `kernel-irqchip=on`, which puts the interrupt controller inside the hypervisor (`macos/run-qemu-gpu.sh:1471-1500`), that incompatibility is not hypothetical here. Owner: QEMU, then Try. Host-sleep pause remains the supported lid-close path in the meantime.

**6.8 MLX on Linux.** MLX is Apple's machine-learning framework for Apple silicon, and this is Joshua Warren's lane in Omarchy M. Relevant only if local models become a persona for this lane; no work item today.

**6.9 DiskImageKit ASIF versus APFS clones.** macOS 27 adds DiskImageKit, a disk-image framework whose ASIF sparse format stacks base, cache and overlay layers, with the guidance that "Shallow stacks perform better" (WWDC26 session 224). That is a potential substrate for 3.4's snapshots and for the factory-disk story, and it should be compared explicitly against today's raw-plus-`cp -c` APFS clone approach rather than adopted on novelty. With macOS 27.0 released, that comparison can be run rather than planned. Owner: Apple, then Try.

**6.10 vmnet port forwarding.** macOS 26 and later support custom topologies on `vmnet`, Apple's host networking framework for virtual machines, with TCP and UDP port forwarding (WWDC26 session 224), which could retire some of the slirp (QEMU's built-in user-mode networking) and `socket_vmnet` machinery behind today's loopback forwards and bridged opt-in. Interesting, not a rewrite trigger. Owner: Apple, then Try.

**6.11 Never, for this lane: nested Windows inside Omarchy.** Omarchy's Windows is Dockur in Docker on KVM with RDP (Remote Desktop Protocol) for display (`omarchy manual/28-windows-vm.md`); section 3's opening records the 64 GB disk floor and the absence of GPU passthrough. It exists for people whose computer is Omarchy. On a Mac, Windows runs beside Try in Parallels, and this lane does not propose, plan, or leave room for Try hosting Omarchy hosting Windows.

## 8. Proposed Mac `docs/V1-READINESS.md` (liftable draft)

Modelled on try-omarchy-windows' `docs/V1-READINESS.md`, the in-family precedent section 1 already dates and quotes, for the four properties worth copying: a one-paragraph scope statement, numbered release gates, per-candidate evidence records, and a sentence distinguishing kinds of evidence. That it was removed once it had done its job is part of the precedent rather than an argument against it. Everything below is a draft for the maintainer to rewrite, not a proposal to adopt verbatim.

### Intended v1 scope

> A dependable Omarchy desktop on Apple silicon Macs, running beside macOS rather than replacing it: a persistent VM whose files and configuration survive app updates, understandable resource controls on a 16-to-24 GB machine, clipboard, camera, audio and folder sharing with the Mac, a runtime update path that does not require a reset, and a documented backup and recovery story.

For comparison, the Windows project's scope sentence is "A dependable Omarchy desktop on x86_64 Windows, with persistent files, understandable resource controls, clipboard and folder transfers, updates, backup and recovery, and configuration export to a native Omarchy installation". The Mac differences are deliberate: no "configuration export to a native Omarchy installation" gate, because on Apple silicon the native destination is Asahi dual-boot on M1/M2 and is a different project's lane; and an explicit memory clause, because 16 and 24 GB unified memory is the binding constraint here in a way it is not on a Windows desktop.

### Shipped baseline

The things a v1 does not have to build are the matrix's **Since 0.4.1** column read together with what was already tagged; entries there carrying a PR number landed on unreleased main after v0.4.1 and are not tagged yet. The merged work behind the baseline is PRs #62, #82, #152, #176, #182, #184, #185, #188, #190, #193, #195, #209, #220, #225, #226, #233, #234, #239, #240, #242, #243 and #246. Under all of it sits the runtime and host-bridge set section 0's security-model paragraph states once and anchors — QEMU 11.1.1 HVF-only with TCG compiled out, camera, audio, two-way clipboard for text and PNG, the one 9p share with host-user semantics, loopback-only TCP/UDP port forwarding at ≤32 rules, sudo Touch ID through the Secure Enclave, and bridged networking as a privileged opt-in — plus the guest 3D chain Mesa virgl → virtio-gpu-gl → virglrenderer → ANGLE → Metal (`README.md:96-131`), VirGL 1.3.0 built from pinned source with the startergo 1.0.42 patches, per-disk paired boot kits that app updates never rebase (`docs/architecture.md:192-225`), an SSH preset that enables `sshd` for one boot (`docs/architecture.md:130-136`), host-sleep pause and resume across lid close over authenticated QMP (`docs/architecture.md:56-64`), nested `/dev/kvm` on M3+ with macOS 26+ (`README.md:364-374`), configurable guest memory and vCPU count (`README.md:150-161, 344-362`), and signed, notarized DMG releases (`.github/workflows/`, GitHub Releases).

### Remaining release gates

These stay one-for-one, in order and meaning, with Decision 5 of the executive briefing; where that document carries the argument, the gate here is the sentence and nothing more.

1. **macOS 27 readiness.** Launch, run and shut down on macOS 27.0 (build 26A428), or a documented "not yet". Already due, not prospective; row 2.1 has the four reports, and see Doc A.
2. **The pipe-2 channel**, at least through the host-bridge layer. Evidence: an existing VM receiving a host-bridge fix through the integration manager, and a documented statement of what pipe 2 does and does not carry.
3. **Video decode: landed or explicitly deferred with evidence** — including the open items already named in review: end-to-end colour accuracy, audio continuity, Firefox, a controlled 60 Hz run, and soak tests.
4. **Memory return validated where people use it.** #243's own remaining-validation list — macOS 26, desktop and graphics workloads, sustained allocation churn — then the picker and a Parallels coexistence envelope written down as the contract on 24 GB and smaller hosts. See row 3.1 and Doc A.
5. **App self-update.** Sparkle or equivalent shipped, or the interim checker declared sufficient for v1. See row 3.5 and Doc A.
6. **A guest CI build path, or an accepted risk.** The workflow records why the guest image cannot be built on hosted runners — "The full build additionally requires privileged ARM64 Docker, which is unavailable on GitHub-hosted macOS runners" — while the runtime now builds in CI on macOS 15 and 26 (`.github/workflows/ci.yml:30-32`, main). A runner or cost decision rather than a Try feature; either answer is fine if it is written down. See Doc A.
7. **Mac-resident table stakes.** Multiple monitors and coexistence with a Parallels Windows VM, or v1 says explicitly "single display, loopback only". See rows 5.1 to 5.3 and Doc A.

### Outside the v1 commitment

Stated so the absence is a decision rather than an omission, and detailed in section 6: Venus / KosmicKrisp / hardware Vulkan in the guest; UEFI boot; USB passthrough and Accessory Access; Keychain, browser passkeys, login or screen-unlock Touch ID, and guest Bluetooth; FEX and x86 application compatibility; multiple concurrent VMs and profiles; guest suspend-to-disk; MLX; guest Snapper/Limine snapshots, structurally inapplicable under direct kernel boot; and running Windows inside the Omarchy guest, a permanent non-goal for this lane.

### Evidence-record convention

Copy the Windows project's sentence unchanged, because it is the part that makes a readiness document hold up in public:

> A code merge, automated test, physical test and public release are distinct evidence.

Practically, for each gate: the candidate change, the evidence type, the machine and OS build it was observed on, and the date. Fail-Safe's M3 Max report on PR #168 is a good worked example of a physical test that is honest about its own boundaries — it reports what was observed and separately records that "End-to-end color accuracy remains unverified".

## 9. Your call: open questions for the maintainer

Each of these is a decision only the maintainer can make. None of them is blocked on anyone answering this document. Where a row already plants the **your call** marker, the question here is a pointer rather than a restatement.

1. **Pipe 2 shape.** Section 1's closing question: does the runtime payload travel as an attached read-only volume, as a dedicated 9p export, or some third way — and does the kernel/headers pair advance through the same mechanism or through a separate, explicitly confirmed boot-kit upgrade?
2. **aarch64 convergence timing.** Row 2.4: when does Try consume the published channel for the Hyprland stack rather than rebuilding it, given omarchy-mac PR #345, edge at the ABI Try pins, and what omarchy-mac PR #354 shows a mistimed switch costs — and is that conversation with the aarch64 package owners worth having explicitly now that omarchy-pkgs #240 and #223 are closed?
3. **Is #92 wanted?** A contributor has a snapshot prototype and no reply. Row 3.4's marker: a direction — yes with these constraints, or no because ASIF layers are the intended substrate — costs one comment and unblocks or closes it cleanly.
4. **Does v1 gate on multi-monitor**, or does v1 state single-display explicitly? Row 5.3 is one sentence either way, and the expensive outcome is neither.
5. **Is the 9p decision a gate or a documented limit?** Row 4.2's marker: if the metadata numbers are poor, does v1 ship virtiofs, or ship 9p with a documented performance note and a recommendation about where to keep working trees?
6. **Guest CI: build it or name the risk?** Gate 6's marker: a self-hosted or ARM Linux runner is a budget question; naming it as an accepted risk is free and honest.
7. **Is the idle screensaver default Try's problem or Omarchy's?** 50 to 63 percent of a core on an otherwise idle VM (row 3.2) comes from a guest default Try can override in its overlay, or that upstream could make VM-aware. Both work; only one is Try's to maintain.
8. **Is a public `docs/V1-READINESS.md` plus milestones and labels the right next process step**, using try-omarchy-windows as the template — or is the current lightweight process working well enough that adding structure costs more than it returns?
9. **Are the input and locale threads one mechanism or four fixes?** Row 4.4 says events answered this on 2026-09-21; what is left of it is whether #181's keyboard-grab question travels with #222.
10. **Which aarch64 tier does Try track, and who carries the rounded-border patch?** Row 2.4: "track stable" and "stop rebuilding" stay incompatible until somebody chooses, and the patch needs an owner either way — upstreamed, carried in omarchy-pkgs, or carried by Try forever.
11. **Is macOS 27.0 support a release blocker for the next tag?** The next release is already large. Whether it ships with #231 and #250 open is a decision, and making it explicitly is cheaper than making it by omission on release day.
